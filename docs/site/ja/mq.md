# MQ

jimble の MQ は **DB のテーブルをキューにします**。
別のミドルウェアは要りません。トランザクションを共有できるのが大きいところです。

## 書く

```java
public class NoticeExecutor extends MqExecutor {

	@Override
	public String queueName () { return "mq_blog"; }

	@Override
	public String key () { return "notice"; }

	@Override
	public MqExecuteType executeType () { return MqExecuteType.short_time; }

	@Override
	public MqStatus execute (DB db, Data row) {

		Data data = row.getDataOptional("data");

		// ... 処理する

		return MqStatus.completed;

	}

}
```

- `queueName()` はテーブル名です。キューごとにテーブルを分けます
- `key()` は種別です。1つのテーブルに複数の種類を混ぜられます
- `executeType()` は `short_time` / `long_time`。取り出し方が変わります
- 戻り値が `MqStatus.completed` 以外なら、`maxRetry()` まで再実行されます


`put()` は**トランザクションの中で呼びます**。
同じ DB なので、ロールバックすれば積んだものも消えます。
「メールだけ飛んで注文が入っていない」が起きません。

時間を指定して積むこともできます。

```java
new NoticeExecutor().put(db, data, scheduledAt);
```

## 二重に実行される

**同じメッセージが2回実行されることがあります。**
処理の途中でプロセスが落ちたときなどです。

なので、**何度やっても同じになるように書いてください**。

- メールなら、送信済みの記録を見てから送る
- 集計なら、足すのではなく入れ直す
- 外部 API なら、冪等キーを付ける

「ちょうど1回」は分散システムでは作れません。jimble はそのふりをしません。

### 処理中のまま残った行

プロセスが処理の途中で落ちると、行は `running` のまま残ります。
**`mq.stale`（既定 10 分）より古い `running` の行は、`mq.recover_interval`（既定 1 分）ごとに `waiting` に戻します**（2.7.8 から。それまではキューを起動するときだけでした）。
戻すのもリトライの1回と数え、`maxRetry()` を使い切った行は `dead` にします。何台かで同時に戻しても、二重には数えません。

> [!WARN]
> **`mq.stale` は、一番長くかかる処理より長くしてください。**
> `mq.stale` より長く処理していると、まだ動いているのに戻され、ほかのワーカーがもう一度処理します（二重に動きます）。
> このとき、あとから終わった古い処理は**結果を書きません**（取ったときの状態のままの行だけ書き換えます。2.7.8 から）。
> ログに「処理している間に取り直されていたので、結果を書きません」と出たら、`mq.stale` を延ばしてください。

```conf
mq {
	stale            = 10m   # これより古い running の行を、落ちたプロセスが残したものとみなす
	recover_interval = 1m    # 戻す間隔。0s なら、キューを起動するときだけ
}
```

## 登録して回す

```java
// テーブルを用意する
new MqQueue(NoticeExecutor.QUEUE_NAME).install();

// Executor を登録する（クラスパス走査はしない）
MqRegistry.add(NoticeExecutor::new);
```

取り出して回すのはバッチです。`MqWorkerBatch` のようなバッチを1つ作り、
[バッチ](./batch) と同じように登録して cron で回します。

**DB から取るのは、キューごとに1本の取り出し役だけです。**取り出し役は、手の空いたワーカーがいるときだけ
`SELECT ... FOR UPDATE SKIP LOCKED` で**手の空いたワーカーの数だけまとめて**取り、その場でワーカーに渡します（先読みはしません。2.5.4 までは1回に1件でした）。
何台で回しても、1件のメッセージを取れるのは1台のワーカーだけです（2回処理されることがあるのは、上の「二重に実行される」の場合です）。
`mq.thread_count.<種別>` は**並んで処理する数**で、増やしても、何もしていないときに DB の接続を借りる数は増えません
（2.1.2 まではワーカーが1本ずつ自分で DB を見ていたので、DB の応答が遅れると、ワーカーの数だけ接続が同時に埋まりました）。

## キューを置くデータソースを絞る

データソースを何本も並べると、キューの表は**全部のデータソースに**作られ、取り出し役は全部を順に見に行きます。
キューを使わない DB（共通の DB など）は外せます（2.7.8 から）。

```conf
db {
	main   { main = true, ..., mq = false }   # このデータソースにはキューを置かない
	shop_a { url = "..." }
	shop_b { url = "..." }
}

mq.queues {
	mq_notice { data_sources = ["shop_a", "shop_b"] }   # このキューを置くデータソース（書かなければ mq = true の全部）
}
```

- 外したデータソースには、**表を作らず、取り出し・迷子の戻し（`recoverStale`）・件数（`pendingCount`）にも行きません**
- 取り出し役は、データソースを名前の順に並べ、**直前に行を取ったデータソースの次から**見ます（2.7.8 から）。
  1つのデータソースに行が溜まり続けても、ほかのデータソースの行は待たされません（取り出し「データソースの数」回の内に見に行きます）
- 両方を書けば、両方を満たすデータソースだけに置きます。`data_sources` に知らない名前があると、起動で止まります
- **外したデータソースの DB に `put` すると、`MqException` になります**（積んでも誰も処理しないため）
- キューの表は、業務の表と同じ DB に置きます。積むのと業務の更新が、同じトランザクションで一緒に巻き戻ります

> [!NOTE]
> **スケジューラのキュー（`scheduler.queue_name`、既定 `mq_scheduler`）は主だけに置きます**（2.7.8 から）。
> スケジューラの管理（`batch_master` など）も、管理画面から積むのも主なので、`db.<名前>.mq` にかかわらず主に作り、主だけから取り出します。
> 主のほかにも積んだ行があっても、もう取り出されません。自分のキューを主だけに置きたいときは `MqQueue.mainOnly("名前")` を使い、
> 積む `MqExecutor` で `mainOnly()` を true にします。

### データソースが 1 つ落ちたとき

データソースを並べていて 1 つが落ちても（つながらない・表が読めない）、**そのキューはほかのデータソースで動き続けます**（2.7.9 から）。

- 取り出し役は、落ちたデータソースを**しばらくあけて見直し**（1 秒から倍々、最大 30 秒）、そのあいだは飛ばします。
  つながらない DB で接続を待たされて、ほかのデータソースの行まで待たされることはありません
- 落ちたとき・見直しても落ちていたとき・戻ったときにだけ、ログを出します（毎周は出しません）
- 迷子の戻し（`recoverStale`）は落ちたデータソースを飛ばし、ほかを戻します。キューを起動するときに 1 つ落ちていても、キューは起動します
- `pendingCount()` は落ちたデータソースを数えずに、ほかの分を返します（それまでは例外でした）
- 取り出し役は、思いがけない失敗があっても終わりません（ログを出して、少し待って続けます）

## 仕事のある DB だけを見に行く

データソースを何十も並べると、取り出し役は**空のデータソースまで毎周**見に行きます。
暇でも、1 つの DB に仕事があるだけでも、データソースの数に比例して SELECT が出ます。
`mq.hint` を書くと、**積んだときに「このデータソースに仕事がある」という印を付け**、取り出し役は印の付いたデータソースだけを見に行きます（2.7.8 から）。

```conf
mq {
	hint           = redis   # off（既定。毎周すべてを見る）| memory | redis
	sweep_interval = 10s     # 全部のデータソースを回る間隔（印の無い行は、遅くともこの間隔で拾う）
}
```

| `mq.hint` | 印の置き場 | 向くとき |
|---|---|---|
| `off`（既定） | 置かない。毎周すべてを見る（これまでどおり） | データソースが少ない |
| `memory` | 同じプロセスの中だけ | 積むのと取り出すのが同じプロセス |
| `redis` | 同じプロセスの中と Redis の集合 | Web で積み、バッチで取り出す（別のプロセス） |

印を使うとき、取り出し役が見るのは次のものだけです。

- 印の付いたデータソース（印を見てから 5 秒は見続けます。積んだ側のトランザクションがまだ確定していなくても取りこぼしません）
- 直前に、欲しいだけ取れたデータソース（まだ残っているかもしれない）
- `sweep_interval` ごとの周は、すべて

**印は「見に行く順を早める」ためのもので、無くても取りこぼしません。**Redis が止まっても、積むのも取り出すのも失敗させず（ログを出すだけ）、全部を回る周で拾います。

> [!WARN]
> **印の無い行は、最悪 `sweep_interval` だけ遅れます。**印が付かないのは、ほかのプロセスが時刻（`scheduled_at`）を付けて積んだ行・`memory` で別のプロセスが積んだ行・Redis が止まっていたときの行です。
> リトライの行は、やり直す時刻の印を取り出し役のプロセスが持つので、遅れません。

手元の MySQL で、キュー 1 本・ワーカー 2 本・`poll_max = 1s`・`sweep_interval = 10s` のときの、取り出しの SELECT の数です。

| データソースの数 | 暇なとき（`off` → `redis`） | 1 つの DB に毎秒 10 件積んだときの、ほかの DB への数（`off` → `redis`） |
|---|---|---|
| 10 | 20 本/秒 → 2 本/秒 | 837 本/秒 → 1.8 本/秒 |
| 30 | 54 本/秒 → 6 本/秒 | 1,701 本/秒 → 5.8 本/秒 |
