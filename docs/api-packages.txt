# 公開 API と内部実装の線引き（要件 NF-C-03 / NF-C-04）
#
# public   … アプリが書くときに触る。1.0 以降、壊す前に非推奨期間を1マイナー置く
# preview  … 外部の仕様に追随する。<b>1.0 の約束の対象外</b>（要件 D-158）
# internal … 実装の都合。<b>予告なく変わる</b>
# empty    … クラスを持たない入れ物
#
# <b>内部は名前で分かる</b>（要件 NF-C-04 / D-160）。
# io.jimble.<モジュール>.internal から下は全部内部で、
# <b>名前と区分が食い違えば ApiSurfaceTest が落ちる</b>。
#
# <b>この表に無いパッケージができても落ちる。</b>
# 増やしたら、どれなのかをここに書くこと（決め忘れだけを塞ぐ仕掛けで、
# どちらにするかを決めるのは人の仕事である）。
#
# 判断の材料：
#   - examples/ が import しているか（していれば公開）
#   - docs/site が名指しで説明しているか（していれば公開）
#   - 入口クラスの内側でしかないか（であれば内部 → 名前に internal を入れる）
